# Threat Model

> **Disclaimer:** This is sample code, for non-production usage. You should work with your security and legal teams to meet your organizational security, regulatory and compliance requirements before deployment. Distributed under the [MIT-0 License](../LICENSE).

STRIDE-based threat model for the Multi-Account Patch Compliance Dashboard. For the corresponding mitigations as code, see [`.kiro/steering/security.md`](../.kiro/steering/security.md) and the three CloudFormation templates under `cloudformation/`.

## Scope and Assumptions

**In scope**: the resources deployed by `cloudformation/{bucket,infrastructure,compute}.yaml`, the Lambda code under `lambda/`, the React frontend under `frontend/`, and the deploy scripts.

**Out of scope**: the customer's existing Resource Data Sync configuration, the customer's IAM roles for AWS Systems Manager Session Manager access, the bastion's Amazon Machine Image (AMI) supply chain, the AWS service control plane.

**Assumed trust boundaries**:
1. Internet → user workstation (out of scope; the user's machine is trusted)
2. User workstation → bastion (gated by AWS Systems Manager Session Manager IAM)
3. Bastion → ALB (private network path, no transit over the public internet)
4. ALB → Lambda targets (AWS-managed Lambda invocation path)
5. Lambda → Amazon Simple Storage Service (Amazon S3) (via Gateway Endpoint, scoped IAM, scoped endpoint policy)
6. EventBridge scheduler → Cache Lambda (AWS service control plane)

## Components

| Component | Trust zone | External-facing? |
|-----------|------------|------------------|
| Bastion EC2 | Amazon VPC private subnet | Yes — accepts AWS Systems Manager session connections |
| Internal ALB | Amazon VPC private subnet | No — `Scheme: internal`, IAM-gated via Session Manager |
| Frontend Lambda | Amazon VPC private subnet | No — ALB target only |
| API Lambda | Amazon VPC private subnet | No — ALB target only |
| Cache Compute Lambda | Amazon VPC private subnet | No — EventBridge invokes |
| Dashboard S3 bucket | AWS-managed | No — bucket policy denies non-TLS, public-access-block on all four flags |
| DataSync S3 bucket | Customer-owned | Out of scope for this threat model |
| ALB access log bucket | AWS-managed | No |
| Amazon VPC endpoints (Amazon S3, AWS Systems Manager, AWS Systems Manager Messages) | Amazon VPC-attached | No — endpoint policy scoped to account principal |

## Security Responsibilities

This threat model is evaluated within the [AWS Shared Responsibility Model](https://aws.amazon.com/compliance/shared-responsibility-model/). The mitigations and residual risks documented in the STRIDE Analysis below assume the following split:

### AWS Responsibilities

AWS is responsible for security **of** the cloud:
- Physical and environmental security of AWS data centers
- Hardware and host operating system patching for AWS services
- Service software patching and availability for AWS Systems Manager (Session Manager control plane), Amazon S3, AWS Lambda, Application Load Balancer, Amazon EC2, Amazon EventBridge, Amazon CloudWatch, AWS KMS, AWS Certificate Manager, and AWS Identity and Access Management
- Service-to-service authentication when AWS services invoke each other (for example, Amazon EventBridge invoking AWS Lambda)
- Annual rotation of AWS-managed AWS KMS keys (`aws/logs`, `aws/sqs`, `aws/ebs`, `aws/s3`)
- Encryption implementation correctness for SSE-S3 (Amazon S3-managed keys) and AWS-managed AWS KMS keys
- Underlying Amazon VPC network infrastructure (route propagation, endpoint connectivity)
- AWS Systems Manager Agent integrity on AMIs published by AWS

### Customer Responsibilities

You are responsible for security **in** the cloud. The threats and mitigations in the STRIDE Analysis assume you have implemented the controls in this template **and** that you operate the deployment correctly after install. Specifically:

**Identity and access management:**
- Issuing IAM credentials only to authorized operators
- Scoping `ssm:StartSession` to bastion-tagged instances ([HARDENING.md](HARDENING.md) recommendation #1)
- Reviewing and revoking unused IAM principals on a defined cadence
- Replacing the self-signed TLS certificate generated by `setup-tls.sh` with a CA-issued certificate before production access ([HARDENING.md](HARDENING.md) recommendation #3)

**Monitoring and incident response:**
- Reviewing CloudWatch Lambda logs, Application Load Balancer access logs, and Amazon VPC Flow Logs
- Enabling CloudTrail data events on the Dashboard bucket if forensic visibility into cache mutations is required ([HARDENING.md](HARDENING.md) recommendation #2)
- Monitoring Amazon SQS DLQ depth and acting on failed Cache Lambda invocations
- Monitoring AWS CloudTrail for unauthorized `ssm:StartSession` calls

**Configuration management:**
- Pinning the bastion AMI to a specific ID and rotating on your patching cadence ([HARDENING.md](HARDENING.md) recommendation #4)
- Switching to a customer-managed AWS KMS key if your compliance posture requires customer-controlled key rotation, lifecycle, or audit ([HARDENING.md](HARDENING.md) recommendation #5)
- Wiring `pip install --require-hashes` into your CI pipeline ([HARDENING.md](HARDENING.md) recommendation #6)
- Enabling MFA Delete on the Dashboard bucket if your compliance posture requires it ([HARDENING.md](HARDENING.md) recommendation #7)
- Configuring the customer-owned Resource Data Sync bucket per your organizational standards (encryption, access logging, lifecycle)

**Change control:**
- Reviewing CloudFormation template changes before applying them
- Re-evaluating this threat model when adding new IAM principals, components, or trust boundaries (see [Review Cadence](#review-cadence))

**Operating environment:**
- Patching, hardening, and securing operator workstations
- Securing the AWS account itself (root credentials, account-level CloudTrail, organizational SCPs)
- Compliance evaluation against any framework you intend to certify under (PCI DSS, HIPAA, FedRAMP, SOX, etc.). Implementing the controls in this workload does not by itself satisfy any compliance framework; see [HARDENING.md](HARDENING.md) compliance scope note.

The STRIDE Analysis below identifies threats specific to the architecture this template deploys, and the mitigations refer to AWS-provided controls or customer-implemented controls accordingly.

## STRIDE Analysis

### Spoofing

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Attacker assumes bastion identity to reach VPC-private services | Bastion uses an instance profile with `AmazonSSMManagedInstanceCore` only. No SSH keys. No public IP. Inbound traffic blocked at security group; only Session Manager arrives via the AWS Systems Manager control plane. The ALB security group accepts ingress only from the bastion's security group via `SourceSecurityGroupId` — no other VPC instance can reach the ALB even with broad SSM permissions. | Compromise of an IAM principal with both `ssm:StartSession` on the bastion and `ec2:ModifyInstanceAttribute` could attach the bastion's SG to another instance and bypass the SG pin. Mitigation: scope `ssm:StartSession` IAM to specific instance tags or ARNs, restrict `ec2:ModifyInstanceAttribute`, monitor with CloudTrail. |
| Attacker forges requests to API Lambda directly | API Lambda is not internet-reachable. ALB has `Scheme: internal`. Only Lambda permission grants are to the ELB service principal scoped to this account/region. | None — non-ALB invocations are blocked by IAM. |
| Attacker spoofs Cache Lambda invocation | Cache Lambda permission grants invoke only to `events.amazonaws.com` with `SourceArn` matching the EventBridge rule. | None for in-account; cross-account principals cannot invoke. |
| ALB serves a forged TLS certificate | ALB listener references a specific ACM certificate ARN. Certificate is generated by `setup-tls.sh` and tagged so cleanup is deterministic. | Self-signed certificate triggers browser warnings on first use. Production deployments should swap to AWS Private CA or organization-issued cert. |

### Tampering

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Cache files modified by an attacker who reaches the Dashboard bucket | Dashboard bucket policy denies non-TLS (`aws:SecureTransport: false`). Versioning enabled — any tampering can be rolled back. Bucket has `BlockPublicAcls`, `BlockPublicPolicy`, `IgnorePublicAcls`, `RestrictPublicBuckets` all `true`. PutObject on `lambda/*` and `frontend/*` is scoped to the deploy principal. Cache Lambda IAM is scoped to `cache/*` only. | A compromised IAM principal with `s3:PutObject` on the Dashboard bucket can still write malicious cache. The 30-minute refresh cycle bounds dwell time. |
| Lambda code package tampered between upload and execution | Same bucket policy, same prefix-scoped PutObject. The Lambda zip is referenced by S3 key (versioning gives rollback). | Without S3 Object Lock, the bucket owner can still overwrite. Object Lock can be enabled in compliance-regulated deployments. |
| Resource Data Sync files modified to inject malicious patch IDs that render in the dashboard | Frontend uses React's JSX rendering everywhere — no `dangerouslySetInnerHTML`. Patch IDs and titles are escaped on render. CSV exports neutralize formula prefixes (`=`, `+`, `-`, `@`, tab, CR). | An attacker who controls the customer's Resource Data Sync bucket can inject misleading text but cannot achieve script execution in the dashboard. |
| Bastion AMI replaced or tampered | AMI ID resolved via AWS Systems Manager parameter `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`. | Trust in the AWS-published AL2023 AMI is assumed. |

### Repudiation

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Operator action on the dashboard cannot be attributed | All access flows through AWS Systems Manager Session Manager → CloudTrail logs the operator's IAM identity, the bastion instance ID, the start/stop time. ALB access logs (90 days, separate bucket) record every request. Lambda logs in CloudWatch (90-day retention). Amazon VPC Flow Logs capture network-level metadata. | Within a single AWS Systems Manager session, individual HTTP requests are not bound to the operator name in ALB access logs — only to the bastion's source IP. Acceptable because session duration is bounded and CloudTrail correlates. |
| Cache write cannot be traced | Cache Lambda emits structured logs with `flush=True` per account/region processed. CloudTrail records every `s3:PutObject` to the Dashboard bucket. | None for the Lambda; CloudTrail data events on the bucket are off by default and can be enabled separately. |
| EventBridge invocation failure not recorded | Rule has `RetryPolicy` (2 attempts, 30 min max age) and `DeadLetterConfig` pointing to `${StackName}-cache-event-dlq`. Failed invocations land in the DLQ with full event payload. | Acceptable. |

### Information Disclosure

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Patch compliance data exposed publicly | All buckets have `PublicAccessBlockConfiguration` with all four flags `true`. Bucket policies deny non-TLS. ALB has `Scheme: internal`. Amazon VPC endpoints are scoped to the account principal. | None for accidental exposure; intentional misconfiguration by an admin is out of scope. |
| Cache contents leak via Lambda logs | Cache Lambda logs aggregate counts and account/region pairs at INFO. Instance-level data (IDs, tags, patch lists) is not logged at INFO. | A bug introducing INFO-level logging of cache contents is possible. Steering file rule against this is captured in `security.md`. |
| Cross-Amazon VPC traffic intercepted | Internal-scheme ALB serves HTTPS only with `ELBSecurityPolicy-TLS13-1-2-2021-06`. Bucket policies deny non-TLS. | None. |
| API responses leak unintended cache fields | API Lambda strips `missingPatches` from paginated list responses (added per detail-cache size constraint, also reduces leak surface). Single-instance lookup includes them by design. | Acceptable. |
| Sensitive customer data in Resource Data Sync inventory beyond patches | Cache Lambda IAM is scoped to four specific prefixes. Other content in the customer's DataSync bucket is unreachable through the workload's IAM. | Customer is responsible for what they store in their DataSync bucket. |
| Self-signed certificate fingerprint pinned by attacker for downgrade | TLS 1.3 policy on ALB. Browser warning on first use prompts operator awareness. | Operators trained to verify the cert thumbprint on first connect; replacement with a CA-issued cert removes this entirely. |

### Denial of Service

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Cache Lambda invocations overlap and corrupt cache files | `ReservedConcurrentExecutions: 1`. EventBridge runs every 30 minutes; one execution per cycle. | If a single execution exceeds 30 minutes, the next firing is throttled (acceptable; DLQ catches failed deliveries). |
| Cache Lambda exhausts account Lambda concurrency | `ReservedConcurrentExecutions: 1` caps it. APILambda is capped at 25 and FrontendLambda at 50, with paired CloudWatch throttle alarms; ALB-driven traffic is bounded by the human-in-the-loop access pattern. | Acceptable for the access pattern (single operator, organization-restricted access). Throttle alarms surface the cause when a cap is reached. |
| Resource Data Sync bucket grows unboundedly and exhausts Cache Lambda memory | Cache Lambda processes one account/region at a time, with 1000-instance batches. Detail caches are written incrementally and chunked into 500-instance files for accounts >500. | Memory is bounded by single-account batch size (~ tens of MBs). 15-minute timeout caps wall-clock cost. |
| EventBridge target failures cause permanent loss | RetryPolicy: 2 attempts, 30-minute max age. DLQ retains failed events for 14 days. | Acceptable. |
| ALB exhausted by request flood | ALB has burst capacity, traffic comes only through SSM Session Manager and is gated by AWS Systems Manager session count. | Acceptable for the human-in-the-loop access pattern. |
| Empty Dashboard bucket on first load | Deploy script invokes Cache Lambda once and waits for completion before printing the AWS Systems Manager access command. | First-deploy timing handled. |

### Elevation of Privilege

| Threat | Mitigation | Residual |
|--------|------------|----------|
| Compromised Cache Lambda role used to read non-Resource-Data-Sync buckets | IAM role scoped to four prefixes on DataSync (read) and `cache/*` on Dashboard (read-write). Amazon VPC endpoint policy further constrains: DataSync allows whole-bucket read; Dashboard allows only `cache/*`, `frontend/*`, `lambda/*`. | DataSync bucket is whole-bucket scoped at the endpoint (intentional, allows new inventory types without redeploy). The IAM role caps blast radius. |
| Compromised API Lambda role used to write to Dashboard bucket | API role has `s3:GetObject` on `cache/*` only. No write permissions. | None. |
| Compromised Frontend Lambda role used to read cache or write anywhere | Frontend role has `s3:GetObject` on `frontend/*` only. | None. |
| Bastion privilege escalation via metadata service | IMDSv2 required (`HttpTokens: required`, `HttpPutResponseHopLimit: 1`). | None on the bastion itself; broader account compromise is out of scope. |
| Lambda execution role used to invoke other Lambdas | Per-function roles. No `lambda:InvokeFunction` granted to any Lambda's role. | None within the workload. |
| Cross-account principal abuses S3 Gateway Endpoint policy | Endpoint policy condition `aws:PrincipalAccount: !Ref AWS::AccountId` restricts to the workload's account. | Cross-account DataSync targets are documented as an extension requiring explicit endpoint policy update. |
| Compromise of one Lambda role to affect another | Per-function IAM roles, no shared roles. CloudFormation generates role names so redeploys can't reuse a stale role. | None. |

                           │ Boundary 1: AWS STS / AWS Systems Manager authn
┌──────────────────────────▼──────────────────────────────────────────┐

## Residual Risks Worth Watching

These are risks the architecture does not eliminate. They should be monitored or documented as accepted by the deployment owner. For implementation steps to address each, see [HARDENING.md](HARDENING.md).

- Replace with AWS Private CA or organization-issued certificate for production.
2. **Bastion AMI trust** — assumed trust in AL2023 AMI. Customers with stricter requirements should pin to a specific AMI ID and rotate on a defined cadence.
3. **CloudTrail data events on Dashboard bucket** are off by default. Enable separately for full forensic visibility into cache writes.
4. **Cross-account DataSync** requires extending the S3 Gateway Endpoint policy with the remote bucket ARN and the remote account principal.
5. **Lambda dependency drift** — `requirements.txt` is pinned but hash-verified install (`pip install --require-hashes`) is documented but not yet wired into CI.
6. **MFA Delete on Dashboard bucket** is not enabled (cannot be set via CloudFormation, would break `deploy.sh delete`). Compliance-regulated deployments can layer it on post-deploy.

## Review Cadence

Re-review this document when any of the following changes:
- A new AWS service is added to the architecture
- A trust boundary changes (e.g. cross-account access, public endpoint)
- A new IAM role or principal is granted access to the Dashboard bucket
- A new Lambda invocation path is added (HTTP route, EventBridge rule, S3 trigger)
- The bastion or Amazon VPC topology changes
